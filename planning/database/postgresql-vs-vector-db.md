# PostgreSQL vs Qdrant Vector Database

## Architecture: Complementary Dual-Storage Pattern

The platform uses a **hybrid dual-store architecture** combining **PostgreSQL 16** (relational system of record) and **Qdrant** (high-throughput vector database). 

Rather than treating them as competitors, each database is assigned the workload it is fundamentally optimized for.

```
                   ┌──────────────────────────────────────┐
                   │       Spring Boot Orchestrator       │
                   └───────┬──────────────────────┬───────┘
                           │                      │
           Write canonical │                      │ Store vectors &
           state & metadata│                      │ query top-K ANN
                           ▼                      ▼
             ┌─────────────────────────┐  ┌─────────────────────────┐
             │      PostgreSQL 16      │  │     Qdrant Database     │
             │   (System of Record)    │  │ (Vector Similarity Index)│
             └─────────────────────────┘  └─────────────────────────┘
```

---

## 1. PostgreSQL: Authoritative System of Record

PostgreSQL is the single source of truth for all business-critical, transactional, and relational data requiring strict consistency:

- **User & Security Data**: Accounts, BCrypt password hashes, roles, authentication profiles.
- **Report Lifecycle & Status**: `ACTIVE`, `RESOLVED`, `CLAIMED` status states; custodial audit trails.
- **Relational Integrity**: Foreign keys between users, lost items, found items, claims, and images.
- **Structured Search**: SQL queries filtering by date ranges, user IDs, coordinates, and cities.
- **Ownership & Claims Workflow**: Verification answers, reviewer notes, proof attachments, and handover logs.
- **ACID Guarantees**: `@Transactional` boundaries protecting item state changes from race conditions.

**Tables**: `users`, `lost_items`, `found_items`, `item_images`, `claims`, `notifications`, `candidate_matches`.

---

## 2. Qdrant: Vector Similarity & Candidate Retrieval Engine

Qdrant is a specialized, open-source vector database built in Rust, optimized for high-dimensional Approximate Nearest Neighbor (ANN) search using HNSW indexing:

- **Vector Storage**: Stores 512-dimensional normalized float vectors generated by the Python AI service (CLIP/vision models).
- **Sub-10ms Retrieval**: Performs lightning-fast cosine similarity lookups across tens of thousands of image vectors.
- **Payload Pre-Filtering**: Attaches lightweight metadata payloads to vectors so queries can filter before similarity scoring:
  - `item_id`: Link back to the PostgreSQL entity ID.
  - `category`: e.g. `"ELECTRONICS"`, `"BAG"`, `"WALLET"`.
  - `city`: e.g. `"Bhubaneswar"`, `"Seattle"`.
  - `report_type`: `"LOST"` or `"FOUND"`.
  - `status`: `"ACTIVE"`.

## 3. Data Flow & Synchronization Pattern

### Write Path (Item Submission)
1. User submits report with image $\rightarrow$ Python AI service generates 512-dim embedding.
2. Spring Boot persists the authoritative report and image metadata to **PostgreSQL** inside a transactional boundary.
3. Spring Boot upserts the vector into **Qdrant** collection `item_embeddings`:
   - `id`: UUID or stringified `item_image_id`.
   - `vector`: `[0.012, -0.043, ...]`.
   - `payload`: `{ "item_id": 42, "category": "BAG", "city": "Seattle", "status": "ACTIVE" }`.

### Read / Search Path (Matching Pipeline)
1. When a new item is ingested, Spring Boot queries **Qdrant**:
   - Filter: `status == "ACTIVE" AND category == :category AND report_type != :currentType`.
   - Vector: New item's 512-dim embedding.
   - Limit: Top 50 nearest candidates.
2. Qdrant returns candidate `item_id`s with raw visual similarity scores in $< 10\text{ ms}$.
3. Spring Boot hydrates the full candidate entities from **PostgreSQL** by their primary keys (`findByIdIn`).
4. Spring Boot passes the hydrated candidates to the 6-D `MatchingEngine` for composite reranking (attributes, text, geo, temporal).

## 4. Why Qdrant + PostgreSQL vs Alternatives

| Requirement | PostgreSQL Alone (with pgvector) | Qdrant + PostgreSQL (Chosen Approach) |
| :--- | :--- | :--- |
| **Relational Data & ACID** | Native PostgreSQL | Handled by PostgreSQL |
| **Vector Search Throughput** | Good for smaller datasets; shares CPU/RAM with relational queries | Dedicated Rust vector engine with independent memory cache and high QPS |
| **Scalability & Isolation** | Vector index builds can consume DB memory and impact API latency | Vector indexing workloads are completely isolated from operational database |
| **Payload Filtering** | SQL WHERE clause | Built-in payload indexing and pre-filtering on vectors |
| **Evolution Path** | Harder to migrate out if vector workload explodes | Clean separation of concerns; easy to scale vector cluster independently |
